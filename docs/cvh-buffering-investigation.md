# CVH: остановка загрузки и авторизация

## Реальный CDN, максимальный буфер, 17 сентября 2026

После уточнения пользователя проверки переведены на реальные источники.
`LiveProviderBufferingTest` запускает один переданный эпизод через production resolver,
плеер, Android TV API 36 и декодеры, с настройкой Maximum (120/240 секунд).
Проверка идёт в реальном времени минимум шесть минут (до девяти, если медленное
наполнение не позволило дождаться второго пополнения), без автоматической смены источника
или повторного получения ссылки. HTTP 403/429 останавливает дальнейшие запросы.
Подписанные URL передаются только через локальные игнорируемые аргументы.

В успешном эксперименте с Range начальный ответ остался **200**, Content-Length 180 697 078;
последующие Range `53921173-` и `68643204-` получили 206. Поэтому нельзя описывать
результат как «первоначальный 206 исправил проблему». Также отсутствие onLoadError
не позволяет называть последующие Range попытками восстановления: extractor может
сам запрашивать другую позицию. Причина различия байтового потока требует отделения
от наблюдаемого результата. Проверка реальным CDN важнее ранее зелёных локальных
сценариев: они этот сбой не воспроизвели.

Правка ограничена выбранным progressive MP4 CVH. Перед следующим чтением после
20 секунд без положительного чтения DataSource выдаёт обычную I/O-ошибку, **не читая
байты старого ответа**. Media3 закрывает ответ и продолжает тот же URL с логической
позиции extractor, сохраняя MediaItem и очередь. Это не общий таймаут запроса:
непрерывное чтение обновляет отсчёт; ссылка не заменяется, metadata resolver повторно
не вызывается. HLS/DASH, другие провайдеры, субтитры и загрузки не затронуты.
20 секунд соответствуют текущему read timeout транспорта; бездействие потребителя
при полном буфере обычный read timeout не контролирует. Причина некорректных байтов
после простоя CDN отдельно не установлена, поэтому это защита пути продолжения,
а не доказательство неисправности сервера или протокола TCP.

Локальная проверка безопасности дополнительно использует настоящий
`DefaultExtractorInput`: прерванное чтение части NAL-prefix и чтение с peek-buffer
не продвигают логическую позицию; повторное открытие восстанавливает точные байты.

Проверка Kodik выявила отдельную регрессию запуска из v1.4.57 (`69a2acf`):
`kodikParams()` искал `promo-error-box` и сообщение во всём исходном HTML. Реальная
страница содержит этот текст в JavaScript-шаблоне, который добавляется только при
открытии плеера вне iframe (`!isIframe()`). Сам плеер и все параметры для API на
странице присутствуют. Приложение ошибочно считало эту страницу недоступной и
не выполняло API POST; это повторилось на двух разных аниме. Первоначальная трактовка
ответа как удалённого видео была неверной.

Из проверки сообщения ошибки исключены script/style/comment-блоки. Извлечение
конфигурации продолжает читать исходный HTML со скриптами. Регрессия с условным
JS-шаблоном теперь выполняет GET → POST → stream; настоящая страница ошибки
по-прежнему останавливается после GET. `ProviderStreamResolverTest`: 13/13.

Итоговая локальная валидация этой правки: 38 app + 13 data targeted-тестов прошли;
debug/instrumentation APK и release/R8 APK собраны. Lint: 0 ошибок, 117 предупреждений,
1 hint. Найденный lint-блокер в существующем `PlaybackNetworkProgress` устранён
добавлением явного Media3 `UnstableApi` opt-in; алгоритм счётчика не менялся.
`git diff --check` проходит. Live-проверки выполнялись последовательно на Android TV
эмуляторе API 36, по одному видео, с остановкой при HTTP 403/429. Повторная загрузка
метаданных и внешний автоматический выбор другого источника в harness отключены:
их запросы не могли скрыть остановку загрузчика или создать цикл обращений к CDN.

Материалы каждого прогона находятся локально в игнорируемом `build/player-audit/`
(`live-*-instrumentation.log`, `live-*-runtime.log`). Публичный код теста не содержит
реальных подписанных media URL. Для ручного запуска `LiveProviderBufferingTest`
нужен аргумент `liveVideo`: base64 JSON с `id`, `animeId`, `sourceName`, `url`
(iframe источника), необязательным `durationSeconds`. Без аргумента live-тест
пропускается и не обращается к источникам. Все результаты выше относятся к обычной
скорости воспроизведения и Maximum; звук физического ТВ и отсутствие всех возможных
долговременных сбоев ими не подтверждаются.

Регрессионные тесты Maximum на синтетическом файле были остановлены после просьбы
пользователя проверять реальные источники; их нельзя включать в число пройденных.
Слышимое качество звука на физическом ТВ этими проверками не подтверждается.

## Проверка на Android TV после повторной жалобы на 1.4.62

Прежние успешные тесты не подтвердили исправление наблюдаемого пользователем
сбоя. Добавлен `RealDecoderBufferingTest`: настоящий Android TV API 36,
Media3 из приложения, `YummyRenderersFactory`, `NativePlayerLifecycle`,
SurfaceView, H.264/AAC-декодеры и AudioTrack. Это выполненный instrumentation
тест, а не только компиляция androidTest. Эмулятор работает без вывода звука
на хост: отсутствие слышимых пропаданий звука на физическом ТВ не проверено.

Синтетический файл длится 180 секунд, содержит 4500 видеокадров и 8439
аудиобуферов. Локальный HTTPS-сервер отдаёт 75% тела, объявив полный размер,
и закрывает соединение. Плеер сначала заполняет Standard-буфер и останавливает
чтение; после начала воспроизведения должен возобновить загрузку и продолжить
оборванный ответ через Range. Использован обычный шаг загрузчика 1 MiB.
Сертификат локального стенда доверен только тестовому клиенту; проверки TLS
и имени сервера не отключены. К источникам запросов не было.

Буфер превышает 70 секунд из-за обычного шага проверки загрузки и малого
битрейта тестового видео. В обоих прогонах загрузчик трижды переходил в
isLoading=true; единственный преждевременный EOF восстановлен внутри Media3.
Проверка сравнивает настройки транспорта, а не два полных APK 1.4.50/1.4.62.

Отдельный `RealTimeBufferingIntegrationTest` выполнил два 180-секундных
JVM-прогона за 362,401 с. Здесь настоящие HTTP, extractor и очереди, но
FakeRenderer вместо декодеров. Android-часы Robolectric продвигаются только
на реально истёкшее время System.nanoTime, без ускорения. Оба варианта
завершились без повторной буферизации и дополнительных сбросов очередей.
Текущий клиент сделал 2 запроса и восстановил 1 ошибку тела; клиент с прежним
20-секундным call timeout — 3 запроса и 2 ошибки. Эта проверка не подтверждает
гипотезу, что отключение общего call timeout само вызывает остановку буфера.

Воспроизводимые команды (длинные тесты занимают около шести минут каждый):

```powershell
./gradlew.bat --offline :app:testDebugUnitTest --tests me.yummydroid.app.ui.RealTimeBufferingIntegrationTest
./gradlew.bat --offline :app:assembleDebug :app:assembleDebugAndroidTest
# После установки debug APK и androidTest APK на Android TV:
adb shell am instrument -w -r -e class me.yummydroid.app.ui.RealDecoderBufferingTest me.yummydroid.app.test/androidx.test.runner.AndroidJUnitRunner
```

Этот результат исключает простое предположение, что любое достижение полного
буфера с последующим обрывом неизбежно ломает текущий плеер. Он не воспроизводит
CDN, токены Alloha, ответы 403, аппаратное декодирование конкретного ТВ или
внешнее состояние выбора источника. Наблюдаемый пользователем сбой остаётся
не воспроизведённым этим сценарием; исправление на его основании не заявляется.

`NativeBufferingLifecycleTest`: 5 JVM-проверок настоящего listener/watchdog
проходят — READY не вызывает таймер, BUFFERING с отсутствием прогресса
вызывает один callback через 3/60 секунд в зависимости от isLoading,
принимаемые байты перезапускают полный интервал ожидания, обновление binding
сохраняет listener и использует новый callback. Эти проверки управляют
состоянием Player и временем явно, поэтому не заменяют сетевые прогоны выше.

`NativeRuntimeLoadTest` выполнен на Android TV за 16,9 с: настоящий runtime
плеера проиграл локальный файл до периодического progress callback; возврат
позиции в binding и 100 обновлений состояния/метаданных не заменили Player
и оставили счётчик загрузок равным 1. Явное увеличение playbackGeneration
увеличило его до 2, сохранив позицию с погрешностью не более 1 с. Это
положительная проверка того, что тест действительно видит повторный запуск.
Две существующие Android-проверки `NativePlayerLifecycleCacheTest` также
прошли. Внешний обработчик ошибок/выбора резервного источника здесь не вызывается.

Дополнительно выполнены `BufferedRetryIntegrationTest` (8),
`CvhBufferingIntegrationTest` (10), `NativeVideoPlayerTest` (28) и указанные
5 lifecycle-проверок: 51 тест, 0 ошибок и пропусков. В сумме с двумя длинными
JVM-прогонами — 53 JVM-теста; на Android выполнены 5 instrumentation-тестов.
Это целевой набор, не повторный запуск всех тестов репозитория. Изменены
тесты, их зависимости/ресурсы и этот отчёт; поведение production-плеера
по результатам данного прогона не изменялось.

## Сравнение с рабочей 1.4.50

По просьбе пользователя база сравнения заменена на тег `v1.4.50`.

| Часть | 1.4.50 → 1.4.61 |
| --- | --- |
| Media3 | Версия 1.10.1 не менялась. |
| Буфер | Тот же DefaultLoadControl, Standard 35/70 секунд, приоритет времени над размером. |
| Аудио | Настройки фокуса, sink и выбора дорожек не менялись; обёртка аудиодиагностики только debug. |
| Оценка скорости | Ручной listener фабрики заменён счётчиком байтов; Media3 продолжает самостоятельно подключать bandwidth meter к HLS/DASH/MP4. ABR не отключён. |
| Реакция на зависание | В 1.4.57 добавлено новое разрешение того же источника с новым playbackGeneration: оно действительно приводит к новому setMediaItem/prepare. Это объясняет перезапуск после сбоя, но не начало остановки загрузки. |
| HTTP CVH | В 1.4.58 добавлен перехватчик с закреплением резервного хоста. В 1.4.50 его не было. |

На этом последнем отличии воспроизведена дополнительная регрессия. Если после
заполнения буфера соединение закрывалось, а первый Range-запрос к основному
серверу временно возвращал 500, перехватчик выбирал резервный и закреплял его
**до проверки успешности ответа**. Ответ 403 резервного оставлял его выбранным
навсегда для текущего поколения, хотя следующий запрос к основному уже мог
успешно продолжить видео.

Локальный стенд с настоящим Media3 сравнил транспорт без перехватчика,
соответствующий этому свойству 1.4.50, и текущий recovery на одинаковых ответах:

- Без перехватчика: основной → Range 82489/500 → тот же Range/206; видео доиграно.
- До исправления: основной → Range 82489/500 → резерв/403 → резерв/403;
  ошибка после опустошения очереди на 9,71 секунды.
- После исправления: отклонённый резерв не закрепляется; следующая отложенная
  попытка возвращается на основной с тем же Range. Видео доигрывается без
  замены MediaItem и дополнительного сброса рендерера.

Ранее работавший резерв тоже перестаёт быть предпочтительным, если его новый
запрос завершился ошибкой. Внутри такого запроса не добавляется немедленный
цикл смены серверов: следующий запрос выполняется по правилам повторов Media3.
Рабочий резерв, известные коды доступа, 429 и Retry-After проверены отдельно.

Это доказанный дефект добавленного маршрутизатора CVH. Он не доказывает,
что именно такая последовательность произошла на ТВ, и не объясняет Alloha,
у которого этого перехватчика нет. Синтетический MP4-стенд не воспроизводит
реальное время простоя CDN или аппаратный декодер. Пороги буфера, выбор формата
и таймеры watchdog по результатам этого сравнения не изменены.

Итог проверки вместе с исправлениями карточек: 1318 тестов без ошибок и
пропусков; `assembleDebug`, `compileDebugAndroidTestKotlin` и
`compileReleaseKotlin` успешны. Запросов к источникам для тестов не выполнялось.

## Повторный сбой на ТВ после 1.4.61

17 сентября пользователь подтвердил, что остановка пополнения и перезапуск
сохранились. Поэтому прежние локальные исправления не считаются решением
наблюдаемого сбоя. Подключённого ТВ/ADB-устройства в текущей проверке нет.

Установлены отдельные пути нового запуска MediaItem: ошибка плеера с выбором
альтернативы; ошибка с новым разрешением источника; таймер начальной загрузки;
таймер отсутствия прогресса в BUFFERING. Таймер BUFFERING не действует в READY,
поэтому сам не объясняет начало остановки пополнения, пока видео ещё играет.
Обычное изменение позиции и обогащение метаданных не меняют ключ загрузки.
Дополнительного доказанного дефекта этих переходов пока не обнаружено.

Стенды 1.4.61 проверяют реальные загрузчики и очереди Media3, но используют
фиктивные рендереры и часы. MP4-стенд с тихим синтетическим AAC уменьшает шаг
проверки продолжения загрузки до 4096 байт, чтобы получить полный буфер на
небольшом файле. Он не воспроизводит реальное время простоя соединения CDN,
аппаратное аудио/видео и полный Compose-путь перезапуска приложения.

Диагностика теперь различает последний триггер и фактический новый load:
ошибка без повторного запуска не является перезапуском. Для триггера нужны
HTTP/error code, состояние, позиция, буфер, isLoading и длительность ожидания;
для load — предыдущее/новое поколение и признак того же URL без самого адреса.
Пока этих данных конкретного сбоя нет, менять протокол CVH, таймеры или число
повторов ещё раз без воспроизводимого основания не следует.

## Предыдущие проверки

Проверка после 1.4.57, 2026-09-16. Видео и API провайдеров для этой проверки
не запрашивались. Использованы сохранённые JavaScript-плееры, исходники
приложения, Media3 1.10.1 и локальные HTTP-стенды.

## Подтверждённый дефект

Правило CVH немедленно возвращало `C.TIME_UNSET` при первом 403. Media3
останавливает загрузчик с фатальной ошибкой, но некоторое время продолжает
выдавать уже накопленные samples. Ошибка становится видимой плееру после
исчерпания буфера. Тогда приложение выбирает альтернативу и выполняет
`setMediaItem/prepare`, сбрасывая накопленный буфер.

Это подтверждённый путь «буфер перестал расти → доиграл → видео запустилось
с того же места». Он не доказывает HTTP-статус конкретного сбоя на ТВ.
Сама неподвижная полоса буфера не является ошибкой: стандартный профиль
накапливает примерно 70 секунд и возобновляет загрузку ниже 35 секунд.

## Подписанные ссылки

CVH получает источники через `/api/v1/player/sv/video/<vkId>`. В изученном
плеере нет протокола обновления медиатокена через WebSocket, как у Alloha.
Внутренний CDN-загрузчик читает текстовый числовой код неуспешного ответа:

| Код | Значение |
|---|---|
| 1 | Истекла ссылка |
| 8 | Ограничение за частые запросы |
| 10 | Изменился User-Agent |
| 11 | Запрещён Referer |
| 18 | Изменился IP |
| 21 | Изменился хост |

HTTP-статус хранится отдельно. Нельзя считать любой 403 истечением ссылки
или ограничением частоты. Нативный обработчик принимает только полный короткий
ответ с известным числовым кодом, а не HTML, JSON или числовой префикс длинного тела.

`expires` и `sig` встречаются в логике кеша, но подпись там не обновляется.
`refreshAuthToken` относится к статистике OneStat, а не к медиазапросам.
При ошибке истечения веб-плеер не запрашивает заново API того же видео:
до начала просмотра он может попробовать резервный хост, при окончательном
отказе внешний плеер выбирает другое видео/озвучку. Подставлять новый `sig`
в старые адреса сегментов без знания схемы подписи нельзя.

Основание: `cvh-frame.js`, символьные смещения 297360–298750 (ответы CDN),
1343300–1343600 (обработка ошибки), 1261350–1261760 (резервный хост),
625000–627970 (статистика); `cvh-player.js`, 77151–78390 (API),
155700–157020 (источники), 168869–169610 (окончательный отказ).
Снимки находятся только в игнорируемой `build/player-audit/`.

## Исправления

- Объявленный CVH резервный хост используется внутри HTTP-загрузчика.
  Сохраняются путь, подписанный query, Range и формат. Переключение однонаправленное
  и принадлежит текущему поколению воспроизведения. Оно не запускает плеер заново.
- В 1.4.58 при обрыве тела ответа загрузчик сразу отмечал резервный хост.
  Эта часть оказалась регрессией и отменена после 1.4.59 (см. ниже).
  Приложение не склеивает тела ответов.
- Неизвестный 403 CVH допускает конечные повторы текущей загрузки с паузами
  2 и 5 секунд. Известные ошибки авторизации не маскируются перебором хостов.
  Код 8 обрабатывается как ограничение запросов, даже при HTTP 403.
  Истечение ссылки допускает уже существующее однократное обновление метаданных.
- Таймер зависания учитывает полученные байты, а не только завершённые сегменты.
  При активной загрузке он даёт сетевому восстановлению ограниченное окно
  60 секунд вместо прежнего короткого таймера. Это не срок жизни ссылки.
- Потеря аудиофокуса не считается зависанием. В debug-сборке добавлены
  ограниченные события underrun, декодера, аудиовыхода и эффективной громкости.
  Громкость и правила аудиофокуса не изменены.

Отдельная причина тихого звука пока не воспроизведена. Штатный audio ducking
может снижать эффективную громкость при запросе фокуса другим приложением;
это гипотеза для конкретного ТВ, а не установленная причина жалобы.
Устойчивый отказ всех серверов или недостаточная скорость сети по-прежнему
могут прерывать воспроизведение; это нельзя устранить одним правилом повторов.

Проверки: 1259 локальных тестов (917 app, 342 data) без ошибок и пропусков;
`assembleDebug` и `compileDebugAndroidTestKotlin` успешны. Стенды проверяют
однонаправленное переключение, частично полученное тело и Range-продолжение,
отмену запроса, Retry-After, известные коды доступа и защиту от ошибочной
классификации длинного ответа. Физический ТВ в проверке не участвовал.

Первичные источники: [CVH SDK](https://player.cdnvideohub.com/s2/stable/video-player.umd.js),
[CVH frame](https://player.cdnvideohub.com/s2/v2.18.4/frame/index.js),
[Media3 1.10.1](https://github.com/androidx/media/tree/1.10.1/libraries/exoplayer).

## Повторная проверка после 1.4.58

Пользователь сообщил, что до изменений 16 сентября CVH нормально пополнял буфер
и звук не пропадал. Поэтому сравнение выполнено с `c7cc04c` от 15 сентября,
а не только с предыдущим релизом того же дня. На присланном снимке выбран MP4
1080p с известной длительностью и остатком буфера около 44 секунд. Плеер на
снимке приостановлен; один такой снимок не устанавливает причину остановки загрузки.

Подтверждена регрессия транспорта: в 1.4.58 для CVH принудительно отключили
`retryOnConnectionFailure`. Это лишало OkHttp восстановления соединения на
основном хосте до обращения к резервному. Настройка теперь наследуется от
основного клиента, как раньше. Локальный тест с недоступным первым IP и рабочим
вторым IP падает со старым отключением и проходит после исправления. HTTP-запросы
в исправленном варианте идут только на основной хост; дополнительных обращений
к провайдеру для этого исследования не было.

Также отменена введённая 16 сентября смена предпочтения Auto с HLS на DASH:
возвращён прежний порядок HLS → DASH. Фиксированное качество по-прежнему выбирает
MP4, а DASH остаётся доступным резервным форматом. Это возврат прежнего поведения,
а не доказательство того, что именно DASH вызывал пропадание звука на ТВ.

Добавлены интеграционные тесты настоящего Media3 с синтетическим MP4/AAC,
локальным HTTP-сервером, фиктивными часами и аудиорендерером. Проверяются заполнение
и последующее пополнение буфера, частичный обрыв ответа, чистый преждевременный EOF
и начальный 403. Базовый транспорт и новый восстановитель проходят сценарии
обрыва без замены MediaItem и без дополнительного сброса очереди рендерера.
Это не воспроизведение всего приложения на ТВ: аппаратный звук, Compose,
реальные таймеры сокета и поведение CDN эти тесты не проверяют.

Порог буфера, версия Media3, аудиофокус, выбор аудиодекодера и настройки
DefaultAudioSink относительно 15 сентября не изменились. Новое переключение
форматов/источников может сбрасывать аудиовыход; его связь с жалобой пока не
подтверждена. Исчезновение звука и конкретный обрыв на ТВ не считаются устранёнными
на основании одного исправления транспорта. В экранную диагностику добавлены
состояние загрузки, громкость плеера и причина приостановки воспроизведения.

После этих изменений прошли 1265 тестов (922 app, 343 data), `assembleDebug`
и `compileDebugAndroidTestKotlin`. Проверка не обращалась к серверам источников.

## Остановка пополнения после полного буфера: проверка после 1.4.59

Уточнение пользователя: буфер сначала достигает 100% настроенного объёма,
затем не пополняется и доигрывается до нуля. Для progressive MP4 заполнение
останавливает чтение открытого ответа; последующее чтение может обнаружить
закрытое соединение. Сам по себе этот обрыв не означает недоступность сервера.

Подтверждён отдельный дефект обработки такого обрыва. Перехватчик CVH заранее
переводил все следующие запросы на резервный хост, не пробуя Range-продолжение
на основном. В прежних тестах резерв всегда был рабочим, поэтому дефект не
проявлялся. Новый стенд использует рабочее Range-продолжение на основном и
постоянный 403 на резервном. С кодом 1.4.59 буфер опустошается и Media3 выдаёт
ошибку около 9,7 секунды; базовый транспорт завершает 20-секундный файл.

Теперь ошибка чтения тела не меняет хост. Media3 сначала продолжает с основного
сервера со своим сохранённым Range. Если открытие этого запроса не удаётся либо
сервер отвечает подходящей ошибкой, остаётся резервный хост. Проверено и обратное
условие: отказ основного Range-запроса действительно приводит к успешному резерву.
Оба случая завершаются без замены MediaItem и дополнительного сброса рендерера.

Стенд проверяет причинную связь между маршрутизацией и опустошением буфера.
Он использует небольшой полный буфер, принудительный обрыв, фиктивные часы и
аудиорендерер. Реальный таймаут сервера и конкретный сбой ТВ здесь не наблюдались;
перезапуск из Compose и аппаратный звук этим стендом не проверяются.
